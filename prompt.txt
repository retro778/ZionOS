You are the lead Linux distribution engineer and C/C++ systems developer for ZionOS.

Build ZionOS: a real, installable, open-source Linux desktop operating system with English and Hebrew support and optional integrated OpenAI and Anthropic AI assistants.

The goal is a production-quality distribution developed through verifiable milestones. Do actual implementation, build images, run available tests, fix failures, and maintain accurate documentation. Do not deliver only an architecture proposal or a simulated desktop.

## 1. Core architecture

Build ZionOS as a Debian-based Linux distribution.

- Use the current supported Debian stable release, verified against official documentation at project start.
- Record the exact release codename, package sources, and build dependencies.
- Retain the Linux kernel, glibc, Debian package management, and supported upstream security updates.
- Use Debian live-build or a documented equivalent to generate a bootable live and installation ISO.
- Target x86_64 initially.
- Support both UEFI and legacy BIOS boot where the selected build tooling supports them.
- Prefer KDE Plasma as the initial desktop, using supported Debian packages.
- Develop ZionOS-specific applications primarily in C++ with Qt 6 and CMake.
- Use C where appropriate for small system components.
- Shell scripts, packaging metadata, and existing components written in other languages are allowed. Do not rewrite mature dependencies merely to make the whole distribution C/C++.
- Do not implement a new kernel, package manager, browser, cryptographic library, or desktop compositor.

Explain this architecture briefly in the repository documentation, then implement it.

## 2. Linux and UNIX software compatibility

Provide real compatibility through the Debian Linux platform.

- Support APT and .deb packages compatible with the selected Debian release and architecture.
- Support building portable open-source POSIX software from source.
- Include a convenient graphical software manager using supported upstream components.
- Consider optional Flatpak support with clearly documented repository configuration.
- Never claim that every Linux binary, every .deb package, or arbitrary BSD/macOS/UNIX applications will run.
- Document architectural, ABI, dependency, kernel, and licensing limitations.
- Never mix incompatible Debian or Ubuntu repositories.

Verify representative applications, including a browser, LibreOffice, a text editor, terminal utilities, and a small C/C++ program compiled inside ZionOS.

## 3. Desktop experience and branding

Create a coherent, usable ZionOS desktop.

Include:

- Login screen and desktop session.
- Application launcher and task panel.
- File manager and terminal.
- Network settings, audio controls, display settings, and time settings.
- Graphical software installation and update access.
- ZionOS Welcome application.
- ZionOS Settings application or a well-integrated settings extension.
- ZionOS AI assistant.
- About ZionOS dialog with version, base distribution, kernel, and support information.

Reuse existing desktop capabilities and write custom code only where it adds ZionOS-specific functionality.

Apply consistent branding to the boot menu, wallpaper, welcome screen, installer where supported, and /etc/os-release. Preserve upstream attribution and package identity where necessary for compatibility and licensing.

Use original or appropriately licensed artwork and fonts.

## 4. English and Hebrew

English is the default language. Hebrew must be selectable during initial setup and afterward.

- Use Unicode and UTF-8 throughout.
- Provide English and Hebrew translations for all ZionOS-specific user interfaces.
- Use Qt translation tools for custom Qt applications.
- Support correct RTL layouts and mixed Hebrew/English text.
- Keep code, paths, URLs, and terminal commands readable in LTR contexts.
- Include suitable freely redistributable Hebrew fonts.
- Configure English/Hebrew keyboard layouts and a configurable switching shortcut.
- Test Hebrew typing, selection, clipboard operations, filenames, dialogs, and AI conversations.
- Document any untranslated upstream components rather than claiming complete translation.

## 5. Integrated AI

Implement a functional desktop AI assistant supporting user-supplied OpenAI and Anthropic API keys.

Before implementing each provider, consult its current official API documentation. Do not invent model names, endpoints, request schemas, or pricing.

Requirements:

- Separate provider adapters behind a common C++ interface.
- Configurable model selection appropriate to each provider.
- Asynchronous networking and streaming replies where supported.
- Cancellation, timeouts, rate-limit handling, and clear errors.
- No automatic retry that could unexpectedly repeat billable operations.
- English and Hebrew conversations with correct text direction.
- Conversation history stored locally, with delete and disable-history controls.
- Markdown rendering with unsafe active content disabled.
- Optional, explicit attachment of selected text or files.
- Clear provider selection and indication of what will be transmitted.
- Usage information where returned by the provider; do not invent costs.

AI should help users understand ZionOS, explain errors, draft text, translate, and suggest terminal commands.

The operating system must remain fully usable without AI, without API keys, and without an Internet connection except for features inherently requiring networking.

## 6. API keys and execution boundaries

- Never embed API keys in source code, ISO images, Git history, logs, crash reports, or example configurations.
- Use the desktop's supported Secret Service/keyring integration for persistent credentials.
- If secure credential storage is unavailable or locked, offer session-only storage or explain how to unlock/configure it. Never silently fall back to plaintext.
- Do not ask the user to paste real API keys into this coding conversation.
- Provide a local settings interface for entering and removing keys.
- Redact credentials from diagnostics.
- Verify HTTPS certificates.

The AI assistant must run as a normal user.

For the first release, display proposed commands with an explanation and a copy button. Do not execute model-generated shell commands automatically.

Treat retrieved documents, command output, and files as untrusted content. They must not override application permissions or trigger actions.

Do not send files, system logs, or machine information to an AI provider without an explicit user action and a reviewable indication of the data being sent.

## 7. Installation and updates

Integrate a maintained installer compatible with the chosen Debian live-image workflow.

- Support installation to a blank virtual disk.
- Provide user creation, timezone, locale, and keyboard configuration.
- Clearly identify the target disk before destructive installation.
- Never partition or install onto the development host.
- Avoid default credentials in installed systems.
- Document any live-session credentials and live-only privilege settings.
- Preserve Debian security updates.
- Package ZionOS custom components as proper .deb packages.
- Define how ZionOS-specific updates will be distributed and authenticated.

A local development package repository is acceptable during development. Do not pretend a production signing service or hosted update repository exists.

If release signing infrastructure is unavailable, implement and document the release procedure and mark that release requirement as incomplete.
